### Contract gaps and deliberate limitations

1. **Active virtual cards:** no tenant-wide active-card count exists in the inspected contracts. The card shows `—` and explains the missing source; it never displays a prototype count or fabricated zero.
2. **Server-owned flow totals:** reports expose daily values, not seven-day issued/redeemed totals. The cards reuse the Reports page's existing `sumReportField` behavior exactly. A future API could return server-calculated period totals and period metadata; this implementation adds no new financial formula.
3. **Sparse report series:** omitted dates do not establish a zero. The line and bar charts preserve gaps and identify missing values in the tooltip/data table. The existing helper's seven-day KPI aggregation semantics are intentionally unchanged.
4. **Freshness classification:** materialization state exposes timestamps/status, but no report-specific stale boolean or age threshold. The UI warns on non-`COMPLETED` status and shows source times; a completed-but-old snapshot cannot be independently classified as stale without a future API signal.
5. **Audit query mismatch/volume:** backend `GET /audit-logs` treats `actorId` as optional, while OpenAPI/generated code marks it required, so the client passes the required empty string to request the tenant feed. The endpoint has no limit/cursor and returns up to 100 records; only five are rendered. A future contract should make `actorId` optional and paginate/project only required fields.
6. **Actor display name:** the audit contract provides actor IDs, not safe display names. The UI uses a generic staff/system/unknown label and never treats IDs as names. A future tenant-safe projection may provide actor display labels.
7. **Dates/period:** report dates use the existing Reports convention: the last seven Lagos business dates, including today.

## Resilience and request budget

- Initial Overview budget: **four requests total**—executive summary, materialization state, approvals, and audit feed. Both charts and four report KPIs reuse the single executive-summary response.
- In-flight work is coalesced per section within the mounted hook (including StrictMode effect replay); completed user data is not stored in a global cache across sessions. No polling is added.
- A 401 triggers one shared session refresh and at most one retry of that endpoint. A 5xx gets at most one 200ms retry. A 429 is never auto-retried; `Retry-After` is honored or a 30-second fallback is used. The affected section shows a countdown and disables its retry; global refresh is disabled while any section is cooling down.
- Success `{ success, data, meta }` envelopes and required response fields are validated at runtime. Failures are normalized to `OverviewApiError` (status, code, safe title/detail, request ID, and retry deadline); the API's actual `{ success:false, error:{statusCode,code,message,details}, meta }` error shape is parsed without changing the API/client contract.
