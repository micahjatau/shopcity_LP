# Change: Focus Supervisor customer and card workflows

## Why

`docs/repo_review_80.md` identifies a workflow and information-architecture problem in Supervisor → Customers and Supervisor → Cards: both routes currently reuse a broad `CustomerWorkspace` with registration, search, profile edits, ledger context, card assignment/replacement/status operations, implementation-facing copy, and response detail interleaved. Selection of a first search result can also alter the registration form into profile editing. These are source findings from the review; implementation must re-check current source and preserve unrelated dirty worktree changes.

This proposal defines a targeted frontend workflow refactor with two existing routes and four focused tabs, keeping customer/account work separate from physical-card work. The operator approved the bounded tenant-scoped Supervisor/Admin card-discovery API described below and later approved one narrowly route-scoped tablet CSS exception documented in `design.md`. Implementation and launch-matrix evidence are now present and independently reviewed; the full second-pass artifact and final validation remain open.

## Intended changes

- Keep `/supervisor/customers` and `/supervisor/cards`; present `Register customer` / `Manage customers` tabs on the former and `Assign card` / `Manage cards` tabs on the latter. Only the selected tab's primary workspace is shown.
- Separate blank customer registration from selected-customer profile management. Registration includes the first card in the existing atomic customer-plus-card operation.
- Make assignment specific to an explicitly selected, active existing customer without an active card; start with a blank serial field and require a fresh card serial.
- Focus card management on an explicitly located issued card and reveal only its status-appropriate replacement, block, or reactivate action.
- Preserve customer-owned wallet/balance across card replacement; do not create a balance-transfer operation.
- Remove implementation commentary, repeated status/context/linked-history panels, raw backend response display, and default ledger history from unrelated registration/assignment tasks while retaining actionable errors, confirmations, statuses and audit behavior.
- Support directly linkable tabs and customer-context handoff using stable customer IDs plus authoritative detail reload before action; recover duplicate-phone registration by resolving through existing customer search or a safe prefilled Manage customers search.
- Provide Manage cards discovery through the approved read-only `GET /api/v1/cards/management/lookup/{serialNumber}` API, with explicit target selection and authoritative reload.
- Update OpenAPI and the generated client only via repository CLIs (`npm run openapi:export` and `npm run client:generate`); do not hand-edit generated files.
- Define error/retry/idempotency presentation, role/security boundaries, responsive composition, accessibility and an API/RBAC/tenant/privacy plus UI scenario test matrix.

## User requirements versus source-confirmed constraints

**User requirements from the review:** four focused workspaces; one active task per tab; blank registration; customer management separated from card management; explicit customer selection for assignment; no assignment serial inherited from an existing card; card action controls shown per selected operation; removal of implementation-only UI; route-preserving direct-link tabs and ID-based cross-page context; responsive/accessibility quality; and launch tests for duplicate phone/card, blocked customer/card, lost-card replacement, failed requests, retry and role permissions.

**Confirmed current contracts/invariants:** registration requires `fullName`, `phone`, and `cardSerialNumber`, and existing backend service creates the customer and initial card in one transaction with audit/idempotency. Separate card assignment requires `customerId` and `serialNumber`, rejects inactive customer, an existing active card, and duplicate tenant serial. Replacement is a supervisor/admin operation that replaces an active card for an active customer and creates the replacement/audit/outbox work atomically; the wallet belongs to the customer. Customer and card status write endpoints are supervisor/admin guarded. Current card status DTO allows `ACTIVE` and `BLOCKED`; `REPLACED` is terminal. Operator authorization covers only the bounded read-only management lookup specified here; no schema/DB, RBAC-policy, or card-status-policy change is authorized.

**Assumptions requiring implementation-time confirmation:** route/tab query parameter convention; authoritative customer detail/list response fields available to distinguish active card and statuses; exact customer-status transition semantics and whether reactivation applies only to a blocked card attached to an active customer; and precise response/audit visibility semantics. The approved management lookup contract is fixed: only `SUPERVISOR` and `ADMIN`; tenant is always derived from authenticated context and never request-selected; serial matching is canonical and case-insensitive; ACTIVE/BLOCKED/REPLACED cards are discoverable; response contains authoritative card ID, serial, status, issuedAt, blockedAt, replacedAt, replacedByCardId and customer `{ id, fullName, status }`; phone, email, balance, audit/internal actor details are excluded; no tenant-scoped match returns 404; ambiguous canonical matches fail closed (never choose arbitrarily); and requests use the existing card-lookup throttle policy with bounded behavior. The existing cashier `GET /cards/lookup/:serialNumber` remains unchanged, including active-card behavior. Resolve implementation details against source and existing policy without changing those boundaries.

## Scope boundaries

In scope: Supervisor frontend pages and workflow components, existing generated-client calls, focused tests and relevant frontend styling/accessibility. The proposal is intended to preserve current backend behavior, not rewrite customer/card logic.

Out of scope: any API beyond the single approved management lookup; DB/schema/migration changes; RBAC-policy or card-status-policy changes; eligibility preflight contracts; registration without first card; customer/card policy changes; ledger/balance writes; cashier/admin workflow redesign or shared component/logic changes; shared design-system rewrite; unrelated dirty files or existing OpenSpec changes. The sole shared-stylesheet exception is the operator-approved tablet rule gated to Supervisor workflow markers described in `design.md`; Admin/Cashier rendering and behavior remain unchanged. The lookup is for Supervisor/Admin card management only.

## Acceptance criteria

1. On each existing route, exactly one of its two tabs is active and only that tab's task workspace is shown. Tabs are keyboard operable, programmatically identified, and directly addressable by URL; invalid/missing tab state resolves to a documented default without breaking the existing route.
2. `Register customer` starts with a blank form regardless of prior search, selected customer, or deep link. Submission uses the existing registration call with all required fields, including initial card serial, and reports success only when the atomic operation succeeds; success states that both customer and card were registered. No two-request partial-registration flow is introduced.
3. Customer search/manage requires explicit selection before profile/status actions; it presents relevant profile fields and customer status separately from card status. Linked-card context is compact and conditional; ledger entries are not shown by default in registration or assignment.
4. `Assign card` requires explicit selection and freshly loaded authoritative customer details. It blocks ineligible/inactive customers and customers with an active card before enabling submit, and sends a new blank-by-default serial; a selected existing card serial is never copied into that field. Backend remains final authority and conflict response is surfaced truthfully.
5. `Manage cards` requires explicit card selection and shows serial, linked customer identity, current status, and available lifecycle date where provided. Only supported actions are available for the selected card/status. Replacement asks for a fresh serial and confirmation; block/reactivate have action-specific confirmation. `REPLACED` is treated as terminal. No customer status is inferred from card status or vice versa.
6. Replacement uses the current replacement operation for the selected active card and same customer, refreshes authoritative customer/card details on success, and leaves the customer's loyalty balance unchanged; no frontend balance transfer or fabricated ledger effect occurs.
   6a. On duplicate-phone registration, the supervisor can reach the existing customer through authoritative ID-based matching or a safe prefilled Manage customers search; unverified error payload data is not exposed as identity.
   6b. Manage cards uses the approved tenant-scoped management lookup, requires explicit issued-card selection, and reloads the target before write; it exposes only the specified minimal response. Existing Cashier lookup behavior and Admin/Cashier UI remain unchanged.
7. Tab and handoff deep links retain existing routes, encode customer identity by ID (not name), reload the server detail before enabling write actions, and do not trust URL-supplied status/balance/card eligibility. Selecting a task tab pushes a history entry; browser back/forward and direct reload restore the selected tab/context. Search and customer-selection context updates may replace the current entry.
8. Only Supervisor/Admin-authorized controls are rendered for these workflows, while the backend remains authoritative. Client guards do not replace role checks. No sensitive full PII, raw response JSON, internal implementation badges, or diagnostic payload is exposed in staff-facing panels.
9. Pending, validation, conflict, authorization, network/server failure, and uncertain write outcomes remain distinguishable and actionable. A retry after an uncertain state reuses the appropriate idempotency key/payload where safe, prevents duplicate clicks while pending, refreshes authoritative state before any new attempt, and never reports success without a confirmed response. Audit events remain backend-owned and untouched.
10. The four workspaces have focused content, readable status/error announcements, labeled controls, logical headings and focus behavior, visible keyboard focus, and usable tab/action sequences. At desktop and narrow/mobile widths, each selected workspace uses available content width, stacks without horizontal page overflow, and preserves meaningful DOM reading order; inactive workspaces do not stack below the active one.
11. Tests cover route/tab/deep-link state, atomic registration payload and conflict/duplicate behavior, explicit selection/no auto-selection, eligibility and serial uniqueness, card status boundaries, replacement balance preservation, role denial/visibility, retries/errors/audit-preserving existing calls, responsive layout and accessibility.
12. A second-pass review is completed after implementation and before final validation; it maps every Review 80 concern and implementation-order item 1–8 to evidence, residuals or an explicit blocker. It is a review/evidence gate, not an implementation step.
