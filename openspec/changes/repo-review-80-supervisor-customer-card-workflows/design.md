# Design: Supervisor customer and card workflows

## Context and inspected contracts

The review names the existing Supervisor routes and shared `CustomerWorkspace`. Current source confirms the shared component owns customer search/selection, registration/profile form state, customer and card status actions, assignment/replacement, ledger output, notes/badges, and raw action response UI. Current route selection uses an `id` query parameter; registration has a separate flow under `/supervisor/customers/new`, and should be checked as an existing implementation seam before deciding whether it can be reused without changing route behavior.

The current backend contracts establish these non-negotiables:

- `POST /customers` accepts full name, phone, required `cardSerialNumber` plus optional email/staff/branch fields; frontend registration already calls this one operation. The current service validates uniqueness and atomically writes customer, initial card, audit records and idempotency completion. No registration-without-card or two-call registration is permitted.
- `POST /cards` takes customer ID and serial, is Supervisor/Admin-only, and rejects inactive/nonexistent customers, duplicate tenant serials and customers with an active card. Database/service checks remain final authority.
- `POST /cards/:id/replace` and `PATCH /cards/:id/status` are Supervisor/Admin-only; existing service replacement requires an active card and active customer, blocks old card and creates linked replacement; duplicate serials are rejected. Customer owns wallet balance, so replacement needs no balance transfer.
- Card status DTO accepts `ACTIVE` and `BLOCKED`; replacement changes the former card to terminal `REPLACED`. Reactivation is represented by setting a blocked card to `ACTIVE`, subject to the existing backend check that its customer is active. Do not expose arbitrary status values.
- Customer create/profile/status write routes also require Supervisor/Admin; existing audit, CSRF and idempotency behavior is preserved.

These facts validate the review's main architectural direction. The operator explicitly authorized one bounded API addition for Supervisor/Admin card management and later approved one tablet-only, Supervisor-route-scoped CSS rule documented below; neither approval authorizes broader API, policy, or shell-logic changes. Existing OpenSpec 78 covers prototype-driven broad shell/layout structure and evidence; OpenSpec 79 covers search/page UX and layout audits. This proposal is narrower: the Supervisor customer/card task model and its domain-specific acceptance. Do not redo unrelated shell work or claim broad prototype parity from this change.

## User requirements and assumptions

### Explicit review requirements

Four workspaces; focused selected-tab-only composition; blank registration; atomic first-card registration; explicit eligible-customer selection for assignment; dedicated blank serial input; focused management actions; split customer/card status concepts; preserve customer balance on replacement; ID-based cross-page deep links and authoritative reload; removal of implementation commentary and raw response panels; retain functional states, confirmation, audit; test the identified error/security cases; desktop/mobile and accessibility checks; and second-pass review before final validation.

### Assumptions to verify before implementation

1. **Tab URL convention:** review requires directly linkable tabs but does not prescribe query names. Use an existing convention if present; otherwise propose one narrowly (for example `?tab=register` / `?tab=manage`) without changing path. For customer handoff, preserve current `id` query compatibility where used. Document final conventions in tests.
2. **Card discovery:** use the explicitly approved read-only `GET /api/v1/cards/management/lookup/{serialNumber}` management lookup for serial discovery. Its bounded contract is: only `SUPERVISOR` and `ADMIN`; tenant always comes from authenticated context, never request input; canonical/case-insensitive serial lookup; ACTIVE, BLOCKED and REPLACED cards; authoritative fields `id`, `serial`, `status`, `issuedAt`, `blockedAt`, `replacedAt`, `replacedByCardId`, and customer `{ id, fullName, status }`; no phone/email/balance/audit/internal actor details; 404 when no tenant-scoped match; fail closed for ambiguous canonical matches; and use the existing card-lookup throttle policy. Preserve the existing cashier `GET /cards/lookup/:serialNumber` active-card behavior unchanged. This authorization does not permit schema/DB, RBAC-policy, or status-policy changes.
3. **Customer status actions:** review says change customer status, but existing status transitions and their business implications must be verified in service/DTO. Offer only supported transitions; do not assume a blocked customer can be reactivated through every frontend path.
4. **Card lifecycle actions:** “reactivate” maps to current status update `BLOCKED -> ACTIVE`, only when server policy accepts it; “lost” is a user explanation/reason only if the existing request supports one. Do not invent a reason field or new server audit metadata.
5. **Balance proof:** replacement must preserve balance by contract. UI tests may assert no balance-write/transfer call and same authoritative balance before/after, while backend's current replacement tests remain evidence of server semantics. Do not compute balance locally.
6. **Accessibility implementation:** tabs may use existing project component or WAI-ARIA tab pattern; preserve current shell conventions and avoid new component library dependency.

If verification uncovers a need beyond the approved lookup or a policy decision, pause rather than silently broaden scope. Generate OpenAPI and the generated client with `npm run openapi:export` and `npm run client:generate`; never hand-edit generated artifacts.

## Information architecture and route behavior

```text
Supervisor
├─ Customers (/supervisor/customers)
│  ├─ Register customer: blank onboarding form + first card + review + result
│  └─ Manage customers: search → explicitly select → profile/status/context
└─ Cards (/supervisor/cards)
   ├─ Assign card: search → explicitly select eligible existing customer → new serial → review
   └─ Manage cards: locate/select issued card → identity/status → one chosen operation
```

Page headings and shared-shell structure remain owned by current route/shell. Tabs are local to these routes and form a single primary tablist. Only the active tabpanel is mounted/rendered for the visible workflow; preserve necessary form state across tab switches only where intentional and never let selection repurpose a create form. Deep links express task and identity, not status/balance. On navigation, the destination fetches current details through existing APIs and withholds write controls until resolution.

### Customer registration

Prefer the existing dedicated `CustomerRegistrationFlow` as the starting point, subject to verifying it can be composed in the tab without changing the existing `/customers/new` route. Otherwise separate create form state from selected-customer state in a small focused workflow component. Keep required full name, phone and first card serial, optional email; include clear review and action outcome. The review must not imply a serial is reserved by a preflight check; backend registration response decides. Avoid a client-only duplicate phone check as authority. Show duplicate/validation conflict and retain safely editable values. For a duplicate phone, resolve the existing record through the already-authorized customer-search path using the submitted phone, then fetch authoritative detail before offering Manage customers by stable ID. Never trust a conflict payload alone as identity proof. If current APIs cannot safely return the match, offer Manage customers with the phone query prefilled so the supervisor can explicitly select a result; do not invent a lookup endpoint or expose unverified details. Success explicitly says customer and first card registered; available next actions link to customer/card management using returned customer ID.

### Manage customers

No initial auto-selection: initial search and subsequent result refresh must not select index zero unless it is the already-authorized ID explicitly present in URL and freshly validated. Search results are selection controls. Once selected, show relevant profile fields, status, and compact linked-card state; expose profile edit, supported customer status action, and card-management handoff. Remove the default five-row ledger and all fields that duplicate profile context. Balance may remain only as clearly labeled customer account context if current authoritative response supports it; it is not a card property or editable control.

Use a centered content width of roughly 1120px. At desktop widths, let search/results occupy about 40% and customer detail 60%; stack them below desktop widths. Keep the query and compact Search action on one row where they fit. Present result rows on a soft neutral surface with identity, muted contact detail, a labeled customer-status badge, and a clear selected treatment. The detail panel leads with customer identity and separate customer/linked-card status badges, then a Profile section with a single primary Save changes action. Put account status in a separate divided group; show status editing/typed confirmation only after Change status is selected. If the customer projection has a linked-card status but omits its serial, present the status without implying the card itself is unavailable and explain the omitted identifier only where the card summary is shown. Do not expand API data or infer an identifier in the UI.

### Assign card

Use explicit customer search/selection and load authoritative customer detail. The allowed UI condition is an active customer with no active card, derived from current authoritative response and current contract. If data is incomplete or the detail request fails, fail closed: don't enable submit. Start a distinct serial input blank; never seed it from linked card details or search selection. Keep serial availability validation as server-final; a local preflight is permitted only if already supported and cannot imply reservation. A customer with existing active card gets a Manage cards handoff. A blocked/ineligible customer receives truthful status and no write action.

### Manage cards

Provide card discovery through the approved management lookup using an entered/scanned serial. Card selection must bind card ID and customer ID; do not select the first result silently. The lookup is read-only, tenant-scoped from authenticated context, canonical and case-insensitive, supports ACTIVE/BLOCKED/REPLACED cards, and fails closed on ambiguous canonical matches; no match returns 404. It returns only authoritative card ID, serial, status, issuedAt, blockedAt, replacedAt, replacedByCardId and customer `{ id, fullName, status }`; exclude phone, email, balance, audit and internal actor details. It is available only to SUPERVISOR/ADMIN and must use the existing card-lookup throttle policy. Do not change the existing Cashier `GET /cards/lookup/:serialNumber` route or its active-card behavior. Reload the target authoritatively before a write. Select operation first; reveal only its own input/confirmation/action. For active card: replace or block. For blocked card: reactivate only if supported by existing contract and active customer. Replaced/terminal card: details only. A replaced card must not be treated as a candidate for another replacement or status update.

Replacement starts with blank replacement serial, requires review/confirmation of old card, new serial and linked customer; it invokes only existing replacement API. On success refresh card/customer details and display the new card; do not change balance or show fabricated transfer history. Blocking/reactivation confirmations remain action-specific. No UI change may suppress server audit/outbox behavior.

## Navigation and state authority

- Retain route paths; encode selected tab and customer context through URL state in the established app convention. `customerId`/existing `id` holds stable UUID, never a display name.
- Selecting a task tab pushes its URL into browser history on both routes, so back/forward restores tab choices. Replacing search or selected-customer context within a task may replace the current entry rather than adding one entry per keystroke/selection.
- Parse URL values as hints only. Fetch customer/card details from current API, check route/role/tenant errors normally, and verify target consistency before mutation.
- Prevent stale request completion from replacing newly selected customer/card context; clear actionable controls while target changes/reloads.
- Preserve user-entered safe fields across validation/conflict failures. On uncertain write timeout, do not blindly generate a new operation: retain/reconcile idempotency according to existing controller pattern, refresh authoritative detail, and clearly communicate outcome unknown if server cannot establish it.
- No local client logic is source of truth for status, wallet balance, role or eligibility.

## Status, errors, retry and privacy

Render customer status and card status as separately labeled values. Display only values/actions accepted by current DTO/services. Keep loading, empty, no selection, not found/inaccessible, validation, duplicate phone, duplicate serial, already-has-active-card, blocked/ineligible customer, terminal replaced card, forbidden, unavailable and uncertain result states actionable. Do not replace a useful backend error with generic success or expose raw response JSON. Technical diagnostics belong in appropriate logs, not supervisor content.

Disable repeat submission while pending. Preserve current CSRF and state-changing idempotency headers. Registration's create key remains stable for the same logical create attempt and is cleared only after confirmed completion or a corrected/new payload according to current helper semantics. Card assignment/replacement/status retries follow existing request/idempotency code. Refresh server state before reattempt if an outcome is uncertain. Audit logs remain backend-owned; frontend neither fabricates nor removes audit events. Minimize PII in search results and summaries consistent with current privileged customer response and access policy.

## Layout and accessibility

Use current ShopCity shell and component conventions, not broad design-system work. Each route has one selected tabpanel filling the available content region; do not render four stacked forms. Desktop may use paired search/list and detail columns only within the selected workspace when current page patterns support it; narrow screens stack search/results/context/actions in DOM order. No horizontal overflow at supported mobile widths. Tabs have accessible names and selected state; use proper tablist/tab/tabpanel keyboard pattern consistent with app conventions, or semantic links if true tabs cannot provide direct-link keyboard semantics without complexity. Inputs have persistent labels, status/errors have appropriate live regions, destructive/irreversible operations identify target and effect, confirm controls are associated with action, focus stays predictable after tab/navigation/result/error, and focus indicators remain visible. No color-only status communication.

## Approved tablet shell exception

Responsive evidence found the shared sidebar's `Help & Training` label clipped at 768px because the tablet media query narrows the sidebar without setting the component's collapsed state. The operator approved a CSS-only rule in `apps/web/styles/shell-components.css`, restricted to `@media (max-width: 920px)` and `.shell-body:has(.sc-page)`, which visually clips only the `/help` label while keeping its text in the accessible name. The `.sc-page` marker occurs only in the Supervisor customer/card workflow routes. No AppShell/AppSidebar logic, navigation policy, Admin/Cashier route, or non-Supervisor style is changed; Playwright checks the Supervisor treatment and Admin/Cashier isolation at 768px. This is the sole exception to the original shared-shell styling boundary.

## Second-pass and final gate

After the implementation pass, a reviewer conducts a clean second pass before final validation. It must walk through all concerns in `docs/repo_review_80.md` and review order 1–8, inspect actual states/source/tests at each affected route, verify no scope drift/API changes, and classify each row as evidenced, pre-existing/verified, not applicable with reason, or blocked with owner/action. This gate is a task/evidence artifact only; this proposal task does not execute implementation or certify it. Only after the second-pass disposition may final tests, `git diff --check`, changed-path/no-staged scope validation and OpenSpec validation be recorded.
